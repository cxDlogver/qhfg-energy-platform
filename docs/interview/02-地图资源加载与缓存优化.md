## 04. 为什么能源地图采用 TileWMS 瓦片化加载，而不是一次加载全球整图或全部原始数据？

### 【回答要点】

首先解释能源分布数据的大范围、高精度特征；然后区分原始栅格数据、WMS 输出图片、前端瓦片图层三种对象，沿可视范围决定瓦片、服务端生成 PNG、前端合成图像说明机制。对比整图加载：按视图只获取必需空间范围、可独立重试及复用瓦片；同时说明多请求开销、瓦片尺寸、解码和绘制并不会消失。以源码的 `TileWMS`、`tileGrid` 和 `/map/getmap` 验证。

### 【重点回答】

全球能源分布例如风电容量因子或光伏资源，是连续覆盖大范围空间的数据。前端若直接获取完整高精度 GeoTIFF、在浏览器解析大量像元，或者要求服务端一次生成全球超大尺寸 PNG，都会带来不符合当前屏幕显示需求的网络、内存及解码成本。

当前 [Map2D.vue](../../apps/web/src/components/dataService/Map2D.vue) 将 WMS 作为**负责把能源栅格生成指定区域图片的服务**，使用 OpenLayers `TileWMS` 将一次视图拆为多个瓦片请求：

~~~javascript
const qgjMapSource = new TileWMS({
  url: `${baseURL}/map/getmap`,
  params: {
    SERVICE: "WMS",
    VERSION: "1.1.0",
    REQUEST: "GetMap",
    Map: props.qgsMapPath,
    LAYERS: props.tifMapPath,
    FORMAT: "image/png",
    CRS: "EPSG:4326",
    language: locale.value,
  },
  tileGrid: customTileGrid,
});
~~~

~~~text
用户打开/拖动/缩放地图
    ↓
OpenLayers 获取 View 的当前空间范围和分辨率
    ↓
结合 TileGrid 计算当前所需瓦片坐标
    ↓
优先使用仍然有效的已加载瓦片
    ↓
对缺失瓦片生成 GetMap URL（带 BBOX、WIDTH、HEIGHT、图层）
    ↓
调用 /map/getmap，由数据 Provider 生成指定范围 PNG
    ↓
下载/解码图片，交给 OpenLayers 组织叠加绘制
~~~

服务端 [app.ts](../../apps/server/src/app.ts) 的核心入口：

~~~typescript
app.get("/map/getmap", async (req, reply) =>
  reply.type("image/png").send(await provider.image(req.query as Params)),
);
~~~

瓦片化减少的是**一次加载所需要覆盖的区域与输出分辨率**，并允许新区域逐步加载及复用，而不是保证任何时候网络请求数量更少。单张瓦片尺寸过大，会增加单次图片处理与内存压力；尺寸过小，则会增加请求、解码与调度数量。项目 `tileSize: 1024` 需要具体场景实验才能说明取舍，不能直接把它称作所有设备最优参数。

这种方式同时与分层渲染有关：大范围能源数值变成图片展示，而不是将每个原始栅格单元转为前端独立矢量 Feature；详见 [分层渲染 Q12](04-分层渲染与地图交互优化.md)。

## 05. TileGrid 如何决定 WMS 瓦片的范围与分辨率？前端 LOD 与服务端栅格金字塔有什么区别？

### 【回答要点】

解释 `origin`、`tileSize`、`resolutions` 和瓦片坐标在请求构造中的作用，结合实际 `EPSG:4326` 与 `1024×1024` 示范一个范围计算。区分**前端多尺度请求和服务端多精度读取**：TileGrid 有三个分辨率级别不能推出 QGIS 内已预建三个 Overview；真实 SourceProvider 的读取方式也不能假设已按尺度采用金字塔。

### 【重点回答】

`TileWMS` 是 OpenLayers 的瓦片式 WMS（Web Map Service，网络地图服务）数据源，用来将不同地理区域的地图图片作为独立瓦片请求；`TileGrid` 则规定瓦片像素尺寸、网格起点和可用空间分辨率。项目的核心配置来自 [Map2D.vue](../../apps/web/src/components/dataService/Map2D.vue)：

~~~javascript
const customTileGrid = new TileGrid({
  tileSize: 1024,
  origin: [-180, 90],
  resolutions: [0.703125, 0.3515625, 0.17578125],
});

const qgjMapSource = new TileWMS({
  url: `${baseURL}/map/getmap`,
  params: {
    SERVICE: "WMS",
    VERSION: "1.1.0",
    REQUEST: "GetMap",
    Map: props.qgsMapPath,
    LAYERS: props.tifMapPath,
    FORMAT: "image/png",
    CRS: "EPSG:4326",
    language: locale.value,
  },
  tileGrid: customTileGrid,
  serverType: "geoserver",
  tileLoadFunction: function (imageTile, src) {
    // 实际项目通过 fetch(src, { headers: { Token: token } }) 加载图片。
  },
});
~~~

这段配置的输入是当前地图视图、图层标识和坐标系；OpenLayers 根据视图范围与分辨率查找或创建相应瓦片，并把需要的地理区域转化成 WMS 请求参数。对服务端来说，关键参数是：

- `MAP`、`LAYERS`：定位请求的是哪一个能源数据图层；
- `BBOX`：请求的矩形地理范围；
- `WIDTH`、`HEIGHT`：返回的图片像素大小；
- `SRS`：WMS 1.1.0 中表示坐标参考系统的参数；项目原始配置同时写了 `CRS`，最终请求以 OpenLayers 生成的参数为准。

例如在 `0.17578125` 度/像素的瓦片网格级别，宽度 `1024` 像素的一张瓦片理论上覆盖 `1024 × 0.17578125 = 180°` 的经度范围。在这个网格的示例瓦片 `z=2,x=0,y=0` 上，WMS 可以构造类似 `BBOX=-180,-90,0,90&WIDTH=1024&HEIGHT=1024` 的请求。这里的 `z` 是自定义瓦片网格级别，不可与 OpenLayers `View.getZoom()` 无条件视为同一个值；实际请求参数还可能受投影、像素比等因素影响。

后端 `/map/getmap` 接收请求并交给相应 Provider 生成图片：

~~~typescript
app.get("/map/getmap", async (req, reply) =>
  reply.type("image/png").send(await provider.image(req.query as Params)),
);
~~~

因此，当前可由源码证明的是**前端按视图范围和配置分辨率取得瓦片 PNG**。它控制地图资源的请求范围与输出像素精度，但瓦片化不等于对图片进行了额外压缩，也不等于服务端一定保存了三份不同精度的栅格文件。服务端是否使用预生成栅格金字塔（Overview）仍需检查真实数据与 QGIS 配置。

瓦片大小存在权衡：1024×1024 可能减少单屏请求数量，但单张图片的生成、下载、解码与内存压力也会增大；不能未经实测声称它必然优于 256 或 512 瓦片。

当前 `tileLoadFunction` 的实际加载链路还包括：`fetch(src)` 携带 Token 请求头 → 检查响应状态与图片内容类型 → `response.blob()` → `URL.createObjectURL(blob)` → 为 OpenLayers 图片对象设置 `img.src`。代码用 `objectURLs: Set` 记录创建的 Blob URL，并在替换或组件卸载时调用 `URL.revokeObjectURL()` 清理。这是**浏览器临时图片 URL 的生命周期管理**，不能把它误称为自建的持久化瓦片缓存；这段加载函数本身也没有把后面业务查询的 `AbortController` 管理器接入全部瓦片请求。

#### <u>1. 前端级别与服务端数据精度是相邻但独立的两个选择</u>

`TileGrid` 的一个分辨率值表示**地图坐标单位/图片像素**，并决定当前瓦片在地理空间覆盖多大范围；服务端接到 `BBOX` 与 `WIDTH/HEIGHT` 后，可以从中推导请求的空间精度。**LOD（Level of Detail，细节层次）**强调不同观察尺度只处理有必要的细节，但项目中“客户端多级瓦片网格”只能证明不同尺度的图片请求，不证明物理栅格文件已被预先构建多级金字塔。

服务端如采用 GeoTIFF Overview/预生成低精度栅格，可根据目标像素精度优先读较低分辨率影像，减少磁盘读取和重采样；否则服务端可能仍需从全精度数据采样，前端输出是小图片也未必显著降低后端 CPU 或 IO。

当前 Source 模式中存在 `getImage()`、`readRasters()` 及内存像元处理，且对大幅栅格存在内存限制；Real 模式由外部 QGIS 提供地图结果。两者均不能从 `resolutions` 参数直接断言实际已有 Overview。应通过 GeoTIFF元数据、QGIS 设置和单瓦片服务端耗时来证明。

## 06. 为什么私有 WMS 图片需要自定义 tileLoadFunction？Token、Blob 与 ObjectURL 怎样协作？

### 【回答要点】

区分默认 `<img src>` 图片加载与能主动设置 Token 请求头的 `fetch` 加载，追踪 HTTP 响应检查、Blob、ObjectURL、图片赋值、错误状态和释放资源的完整链路。说明前端携带凭据只是请求方式，真实权限必须由后端校验；Blob URL 不是持久化缓存，更不能把 URL 是否可见当作资源安全边界。

### 【重点回答】

当前 WMS 图片不是简单设置图片地址，而在 [Map2D.vue](../../apps/web/src/components/dataService/Map2D.vue) 的 `tileLoadFunction` 中使用自定义加载：

~~~javascript
tileLoadFunction: function (imageTile, src) {
  fetch(src, {
    headers: { Token: `${token}` },
  })
    .then(async (response) => {
      if (
        !response.ok ||
        !response.headers.get("content-type")?.startsWith("image/")
      ) {
        throw new Error("Network response was not ok");
      }
      return response.blob();
    })
    .then((blob) => {
      const objectUrl = URL.createObjectURL(blob);
      objectURLs.add(objectUrl);
      // 后续获取 imageTile.getImage()，再设置 img.src = objectUrl
    })
    .catch((err) => {
      imageTile.setState(TileState.ERROR);
      console.error("Tile loading error:", err);
    });
}
~~~

这段代码把**携带身份凭据的 HTTP 获取**与**供图片元素使用的地址**分开：

~~~text
TileWMS 构造瓦片 URL
  → 自定义 tileLoadFunction 接收 URL
  → fetch 以请求头 Token 发送 HTTP
  → 检查 status 与 Content-Type 为 image/*
  → response.blob() 得到图片数据对象
  → URL.createObjectURL(blob) 创建临时 blob: URL
  → imageTile.getImage() 对应 img.src = blob: URL
  → 浏览器解码图片，OpenLayers 使用已加载瓦片
  → 替换或卸载时 revokeObjectURL 释放临时 URL 引用
~~~

Blob 代表浏览器取得的二进制资源数据，ObjectURL 是它的临时本地引用，供 DOM 图片元素加载。项目用 `objectURLs` Set 记录它们，尝试在旧瓦片图片替换或组件卸载时释放；但不能将它当作永久的网络缓存，也不能说所有内存必然在调用 `revokeObjectURL` 后立即归零。

**安全边界**：浏览器发送 Token 后，仍需要服务端验证请求身份、数据范围和授权；前端隐藏图层、对 URL 做编码或转换为 Blob 都无法替代服务端权限控制。当前应用使用自定义 Token 请求头，是否存在刷新过期、跨用户缓存隔离和权限撤销，还要按对应后端配置核验。

**加载边界**：这条自定义 `fetch` 并没有接入前一题 `identifyNum` 的 `abortControllers` 注册表；因此不能声称点位请求取消会自动控制所有 WMS 图片请求。失败分支将 OpenLayers 瓦片置为错误状态，但仅有错误处理代码不代表已经实现完整重试退避机制。

## 07. OpenLayers、浏览器 HTTP 缓存和服务端缓存有什么区别？什么时候能直接复用地图瓦片？

### 【回答要点】

沿一次请求从“地图数据源 → HTTP 网络节点 → 服务器读取/生成图片”分层解释缓存实体、键、新鲜度、命中与失效。必须区分私有能源 `/map/getmap` 和基础图 `/tiles`；服务器的静态文件读取不是自动存在的 Nginx 代理缓存。讨论多语言、不同地图/图层、BBOX、图片像素尺寸造成的缓存键变化，权限隔离以及服务端原始数据更新后的旧结果风险。

### 【重点回答】

OpenLayers 数据源管理已经获取的瓦片对象与加载状态。地图回到历史区域时，如果相应瓦片仍在缓存中且适用于当前数据源状态，便可以直接复用；否则重新加载。这里属于**框架内置能力**，当前业务代码并没有独立实现 `Map<tileKey, PNG>` 的瓦片缓存管理器，更不能保证所有历史瓦片永久留存。

HTTP 缓存是另一层机制：服务端用 HTTP 响应头声明资源是否可以在浏览器或共享缓存中复用。当前 [app.ts](../../apps/server/src/app.ts) 对基础瓦片接口显式配置：

~~~typescript
app.get("/tiles", async (req, reply) =>
  reply
    .type("image/png")
    .header("Cache-Control", "public,max-age=3600")
    .send(await provider.tile(req.query as Params)),
);
~~~

`max-age=3600` 表示适用缓存的一小时新鲜度寿命，`public` 表示该响应在符合其它协议条件时允许由共享缓存保存。第一次请求成功取得响应后，浏览器可按 HTTP 缓存规则存储；相同请求在缓存仍新鲜且匹配时可以不再访问服务器。

但能源业务图片走的是 `/map/getmap`，其路由没有显式设置同样的 `Cache-Control`。不能据此宣称私有能源瓦片已经配置了一小时的 HTTP 缓存，也不能仅因 Node.js 返回 `Cache-Control` 就宣称 Nginx `proxy_cache` 已开启。带 Token 的私有图层需要额外考虑共享缓存的权限隔离。对应通用机制见 [HTTP 缓存机制知识体系](https://github.com/cxDlogver/cx-learn-notes/blob/main/Full-Stack-AI-NOTES/H-HTTP缓存机制知识体系.md)。

#### <u>1. 数据提供模式中的服务端进程内缓存</u>

当前后端根据 `DATA_PROVIDER` 选择数据提供方式：`fixture` 用于隔离测试，`source` 用 Node.js 读取本地真实原始数据，`real` 将 WMS 请求转交给 QGIS 等实际服务。不同模式不应混同。

`SourceProvider` 在 [source.ts](../../apps/server/src/source.ts) 中定义：

~~~typescript
private cache = new Map<string, Promise<Raster>>();
private images = new Map<string, Buffer>();
~~~

- 原始 Raster 缓存最多保留 **2 份**读取解析结果，减少重复读取 GeoTIFF 和完整栅格数组；
- 已生成 PNG 缓存最多保留 **24 张**，缓存键关联图层、`BBOX`、`WIDTH/HEIGHT` 和坐标系，减少完全相同参数下的重复逐像素计算与 PNG 编码；
- 两种缓存都处于 **Node.js 进程内存**，服务重启后失效，不是磁盘或 Redis 持久化缓存。

`RealProvider` 则把对应 WMS 请求转发给 QGIS Server，现有代码不能证明外部 QGIS 已配置 GeoTIFF Overview、瓦片结果缓存或与 `SourceProvider` 相同的内存缓存。仓库默认 `fixture`，新增 `source` 曾用于本地真实 GeoTIFF 恢复与验证；不能将“存在 `real` 适配器”直接等同于完整生产数据服务已经部署验收。项目事实可继续核验 [README](../../README.md) 和 [恢复验证记录](../../docs/validation/restoration.md)。

#### <u>2. 缓存的一次完整运行过程与失效条件</u>

~~~text
视图需要某张能源 WMS 图片
    ↓
OpenLayers 现有数据源能否复用匹配的瓦片？
    ├─ 是：直接参与地图显示
    └─ 否：发出网络请求
              ↓
        请求是否能被 HTTP 缓存节点按规则满足？
        ├─ 是：复用已缓存响应
        └─ 否：到达 /map/getmap 等服务器接口
                      ↓
             对应 Provider 读取/生成图片
                      ↓
             如果 Source 进程内缓存键匹配，可复用解析结果或 PNG
                      ↓
             返回新响应，客户端解码并显示
~~~

上述图表示多种**可能的复用位置**，不是声称每层在当前运行模式均已启用并命中。OpenLayers 数据源缓存的瓦片通常与具体图层源和参数状态关联；HTTP 缓存依据请求 URI、方法、响应策略、Vary 等匹配；SourceProvider 进程内 Map 依据其自定义的图层、地理范围与输出尺寸等键判断。即使浏览器缓存过期，服务端内存 PNG 缓存若未随原始数据更新而失效，也可能继续返回旧数据。

#### <u>3. 缓存安全与验证原则</u>

- 对公开底图适用的 `Cache-Control: public,max-age=3600` 不应无条件复制到带 Token 的私有能源数据。
- Nginx 直接读取已部署的静态文件，与明确开启 `proxy_cache` 储存上游 HTTP 响应是两件不同的事。
- 相同 URL 在数据版本或权限变化后能否返回新内容，应考虑短 TTL、校验器、版本化 Cache Key、缓存失效和权限隔离；仅凭响应头不能认定 Nginx/CDN 已配置真实缓存节点。
- 用 Network 查看请求发起、响应大小及缓存命中，再结合瓦片生成耗时与内存缓存统计，才能确认节省发生在哪一层。

本篇与下篇衔接：地图瓦片复用由 OpenLayers / HTTP 缓存负责，用户点击返回的结构化数值由业务层 `requestCache` 和 `pendingRequests` 负责，它们的缓存对象与生效条件完全不同。
