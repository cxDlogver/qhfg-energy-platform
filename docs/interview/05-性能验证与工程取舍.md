## 17. 如何建立能源地图加载与交互性能的测量体系？分别用哪些证据验证资源、网络与分层渲染优化？

### 【回答要点】

从**加载体验和运行时交互**两类目标出发组织指标：页面首次进入时关注 FCP、LCP、总字节、请求数及阻塞情况；地图连续拖动和缩放时关注每张瓦片到达时间、解码、主线程执行、Frame Time P95、LoAF、峰值内存；点击查询时关注重复网络请求数、取消成功率、过时结果是否错误更新、单点到图表的完成时间。每个指标必须与具体用户动作、运行环境和可复现的基线绑定。不能使用 Lighthouse 的 TBT 直接替代线上交互 INP，也不能把页面导航结果当作地图 FPS 结论。

### 【重点回答】

当前优化体系沿两条相互关联的链路运行：

~~~text
用户打开或切换能源图层
    ↓
可见瓦片资源：数量、总字节、缓存命中、服务端生成时间、解码与显示
    ↓
地图成为可用状态：页面 FCP/LCP 与热力图首张、全部可见瓦片时间

用户拖动 / 缩放 / 连续点选
    ↓
是否反复请求相同点位？旧请求取消后是否继续错误提交？
    ↓
源/图层/Feature/Style 的更新次数及 JS 计算量
    ↓
Performance：主线程任务、Frame Time P95、LoAF、交互延迟
    ↓
最终检查地图和图表结果是否正确一致
~~~

| 机制 | 直接验证项 | 辅助指标与注意事项 |
| --- | --- | --- |
| TileWMS + TileGrid | 固定视图中的瓦片请求数、BBOX、输出尺寸、总字节、可见瓦片加载结束时刻 | 需同时比较服务端处理和图片解码；减少请求不代表总负担一定减少 |
| OpenLayers 与 HTTP Cache | 返回历史区域时是否仍有网络、请求来自 memory/disk/cache 还是 server | 要保证同一数据、同一 URL、同一缓存状态 |
| SourceProvider Raster/PNG Map | 相同参数重复请求时实际命中、原数据改变后的失效、进程内存 | Source 实现不等于 QGIS 已具备同样缓存 |
| requestCache / pendingRequests | 同一缓存键多次点击是否只发一次请求、TTL 与容量限制是否生效 | 需覆盖 A→A 并发、5 分钟过期、错误分支 |
| AbortController + 序号 | A→B、A→B→A、组件切换和卸载后的网络与 UI 状态 | 请求取消不一定取消服务端实际计算 |
| 分层更新 | 点击只更新 marker 时是否新增 WMS 请求；Feature 分配、DOM 更新次数 | 不要把“无 WMS 回源”推断成“GPU 只重绘一个图层” |
| 动画、图层生命周期 | 不可见时是否停止渲染循环与事件、资源是否清理 | 长时间内存/帧行为需要单独 Soak Test |

公平实验至少固定：代码版本、原始资源和业务数据集、视图中心/缩放、设备、网络节流、缓存状态、账户状态、登录路径、首屏/热切换模式、相同测试轮数及统计口径。**性能收益的正确说法必须带测试对象、条件和前后值**；没有隔离实验的机制不能声称其单独贡献了全部综合分数变化。

#### <u>1. 当前仓库已采用的导航测量协议和验证范围</u>

本机记录日期 2026-10-07，时区 Asia/Shanghai。原始目录保持只读；仅在目标目录制作私有冻结副本。source-fingerprint.json 可核对原文件指纹，不含凭据值。

- 原版副本：.local/baseline-web；保留原模板/CSS/字体/GIF、全量库注册及构建分块。只将 API、地图、天气改到同一隔离 fixture；补挂载原 static 目录及 Cesium 插件资源，不把缺失资源 404 当作性能优势。
- 新版：apps/web 的 Vite production dist。两者由同一个 scripts/serve.mjs 提供相同压缩和 API 代理；不测 Vite dev。
- Node 24.19.0 / Lighthouse 13.5.0 / Chrome 154.0.0.0 / Windows。桌面 1920×1080，移动默认模拟；完整配置写在 scripts/lighthouse.mjs 和每轮 LHR.configSettings。
- 每轮创建独立 Chrome profile，先通过实际本地表单登录 demo_download；数据页通过菜单写入默认2021结果并确认图例可加载。disableStorageReset 保留该状态，浏览器资源缓存由 Lighthouse 冷启动。
- 首页、数据页 × 桌面、移动 × 3轮 × 原版、新版，最终公平对照共24轮；另保留12轮即时压缩探索基线（baseline-on-demand）与12轮WebP候选（optimized-webp），不混入最终统计。设备/页面分别取各指标中位数，同时保留 min/max；不从三轮中挑最好成绩。
- 指标：performance score、FCP、LCP、SI、TBT、CLS、total-byte-weight。TBT 不等于线上 INP；模拟 LCP 不等于真实墙钟。三维新增能力单独报告首次显示/业务响应、隐藏零帧/keep-alive恢复，不与不存在的旧入口比较。
- 原始JSON/HTML公开仅含本地 fixture URL与测试数据；不公开 Chrome profile、真实环境变量、JWT headers、私有生产数据或源码凭据。
- 优化前后审计不与资源编码/构建任务并发，减少本机 CPU/磁盘竞争。真实数据服务延迟、外网地图、网络状态不能从该本地报告推断。

#### <u>冻结原版重现</u>

历史测量基线来自用户提供的 QHFG.Web；没有把该私有原工程或其 node_modules 发布到新仓库。拥有原始源码时，复制前端到 .local/baseline-web（排除.git/.svn/node_modules/旧报告），提供该前端原锁文件对应的依赖，设置所有外部业务请求为 /api、天气为 /api/weather、天地图为 /api/tiles，并保持原样式与资源。

然后运行 node scripts/baseline.mjs，在一个终端启动 node scripts/serve.mjs baseline、另一个终端启动 fixture API，再执行 node scripts/lighthouse.mjs baseline。此命令使用原依赖入口，不向原始目录写入。原版 static 没有在 Vite public 内，因此预览服务器补挂载；原插件的 Cesium 静态资源必须完整而非404。

#### <u>优化目标（基线之后设定）</u>

优先保证行为/样式和资源等价；性能目标是减少首屏非必要 JS、避免二维加载 Cesium、缩短 FCP/LCP、减少总传输量并控制 TBT/CLS。未承诺任意网络环境下固定90分；保留完整大动画/中文字库会限制最大传输降幅。全部轮次与未达标情况均记录，结果没有取代真实服务验收。

#### <u>预览服务器校正</u>

初始12轮基线使用按请求即时 Brotli 压缩。三维冷加载实测15.15秒后查得数值参数0实际是 MODE，并非 QUALITY，造成默认高压缩级别的服务器CPU延迟。用 Node zlib.constants.BROTLI_PARAM_QUALITY 明确设4，并在两个预览启动时预压缩同类资源、按mtime失效。修正同时作用于原版和新版；原12轮保存在 reports/baseline-on-demand，最终原版12轮全部重测，不与不同服务策略比较。浏览器缓存仍保持冷启动，服务器压缩缓存用于模拟已准备的生产静态资产。

#### <u>最终候选</u>

WebP有完整像素等价，但首批移动TBT与分数退化。最终保留原GIF，继续完整WOFF2与按需代码；#app的flow-root解决边距折叠造成的整页位移，OpenLayers Map/Layer使用shallowRef以保留第三方对象身份。七页静态像素复核仍为0差异；全部候选原始报告保留，最终12轮不得沿用WebP候选值。

#### <u>2. 仍应增加的地图操作专项性能实验</u>

相同区域与图层下可以分四个独立 Case：首次可见瓦片完成；拖动缩放返回原视图；连续点击同一与不同坐标并检查最终弹窗；仅移动 marker 与切换能源 Source。每个 Case 同时保存 Chrome Network、Performance Trace、接口请求日志和功能断言，并对结果取多轮中位数/波动区间，记录失败与回退。当前公开 Lighthouse 导航报告并不能自动证明这些 Case 的全部性能目标已经达成。

## 18. 项目目前有哪些可复现的性能提升？有哪些回退和没有消除的瓶颈？

### 【回答要点】

必须完整说明最终对照是在**同一 Fixture、本地预览与登录状态**下进行原版/优化版 24 轮 Lighthouse 导航测试，区分桌面/移动、首页/数据页，完整呈现分数、FCP、LCP、Speed Index、TBT、CLS、传输量。对移动数据页 **55→43** 和 **TBT 0→998 ms** 不回避，也不把移动 FCP/LCP 的模拟秒数当作真实墙钟时间或将 TBT 当成 RUM INP。说明 GIF、字体、WebP 回退、预览服务器压缩修复等影响因子。

### 【重点回答】

[最终指标报告](../performance/results.md) 保留了正式公平对照的全部中位数、资源约束与回退说明。其中最重要的两组结论是：桌面数据页 FCP 16.35s→8.96s、LCP 16.63s→9.42s、传输 20.23MB→11.28MB，但分数仍为 55；移动数据页 LCP 102.92s→57.30s、传输 20.23MB→11.27MB，同时 TBT 0→998ms、分数 55→43。这说明资源减少与总体验指标改善并不等价。所有数字都属于模拟条件下的本地导航审计，**不代表生产真实 QGIS/数据库/外网表现**。

后续重构时，首页按需加载业务依赖，三维 Cesium 在首次进入三维时再加载，不可见时暂停无价值的渲染循环；保留原二维已有的缓存、取消和 Blob URL 生命周期机制。浅引用使 OpenLayers 等第三方实例避免不必要的 Vue 深响应式代理，但没有单变量对照证明它贡献了多少分数，不能强行归因。

本项目还保留了失败方案：完整 GIF 转 WebP 候选尽管画面和时序等价，移动端的性能指标退化，因此没有纳入最终方案；保留全量字形字体与 GIF 动画也使大资源瓶颈尚在，不能通过删减原素材伪造提升。移动数据页的初始化阻塞需要后续针对真实交互进一步分析。

#### <u>后续可评估优化</u>

- 在真实部署保持相同资源时，预压缩、内容哈希与长期缓存/CDN可减少后续访问成本；需用真实环境重新测量。
- 若将来允许资源策略变化，可评估动画分段加载/尺寸响应或完整字库分包；应先证明全字符覆盖、字形与动画节奏等价，不能直接裁中文字符或替换为静态图。
- 在真实QGIS环境测地图瓦片/点查/统计耗时，单独区分网络、服务、数据库和前端交互；使用现场真实用户指标补充导航Lighthouse。

#### <u>明确保留的回退</u>

浅引用优化保留外部对象身份，但本次没有隔离单变量测量，不能把整体分数变化全部归功于shallowRef。依据 [Vue文档](https://vuejs.org/api/reactivity-advanced.html#shallowref)。

## 19. Fixture、Source、Real 三种运行模式分别验证什么？实际能源数据与生产能力的证据边界是什么？

### 【回答要点】

区分测试用的模拟数据、从本地真实源文件恢复的数据、以及依赖外部 QGIS/数据库等的正式适配器。分别回答“接口交互能否跑通”“能源数值是否来自真实地理数据”“覆盖哪些能源/年份”“是否完成生产安全和性能验收”，并把原始项目经历和后来公开仓库的改造与测试分开，不能把 2026 年新接入的三维能力写成原项目时间段已有的路由功能。

### 【重点回答】

当前 [app.ts](../../apps/server/src/app.ts) 根据 `DATA_PROVIDER` 选择具体实现（以下为简化说明，并不代替源码的启动校验）：

~~~typescript
// 机制性简化：实际代码包含模式检查及异步初始化
const mode = env.DATA_PROVIDER ?? "fixture";
const provider =
  mode === "source" ? await SourceProvider.create(env) :
  mode === "fixture" ? await FixtureProvider.create() :
  new RealProvider(env);
~~~

## 20. 如果继续优化能源地图性能，应如何决定优先级、选择技术方案和验证取舍？

### 【回答要点】

沿“场景与症状 → 指标 → 排除其它干扰 → 找到实际成本 → 提出小范围变更假设 → 同条件重复实验 → 功能/视觉/安全验收 → 保留或回滚”的完整闭环回答。结合实际的 1024 瓦片、TileGrid 精度、GeoTIFF Overview、客户端/服务端缓存、Source 重建、样式/Feature 复用、字体/GIF 策略和移动 TBT 回退展开。要论证为什么减小传输、增加缓存、提高预加载并不一定使整体体验更好；真实源数据范围、私有数据授权以及视觉等价都是实验约束。

### 【重点回答】

优化工作必须先确定用户目标：是首次打开全球图层太慢，缩放时出现白块，连续点选显示旧值，还是地图拖动掉帧？四种症状对应不同成本来源，不能用统一的“性能差”推出同一种技术方案。

~~~text
用户动作与失败现象
    ↓
统一数据、视图、设备和缓存状态
    ↓
收集 Network、Performance、服务端耗时、内存和功能正确性证据
    ↓
判断主要瓶颈
    ├─ 地图图片加载：瓦片尺寸、可视范围、缓存命中与网络条件
    ├─ GIS 服务端计算：GeoTIFF 读取、Overview、窗口化与 PNG 编码
    ├─ 业务网络请求：重复结果、在途 Promise、取消和过时状态
    ├─ 主线程与图层：脚本初始化、Feature/Style 分配、绘制帧
    └─ 大型资源：GIF/字体/三维代码是否在当前页面必要
    ↓
单次只修改少量可归因的变量
    ↓
测量优化后指标和功能/权限/视觉回归
    ↓
多轮统计并保留失败结果与回滚理由
~~~

#### <u>1. 地图加载精度与服务端处理需要联合设计</u>

目前 TileGrid 使用 1024 像素瓦片及三个前端空间分辨率级别。改用小瓦片可能减少视图外的过度加载，但增加请求、调度和图片解码数量；大瓦片可能减少请求，单张下载/处理更重。必须比较固定视图的总字节、首张和全部可见瓦片完成时间、地图平移后的新增请求和内存。服务端真实 GeoTIFF 如果每次仍需处理大幅高精度数据，减小客户端图片尺寸不等于根本降低 IO；应在真实 QGIS/Source 环境测量是否需要 Overview、按地理窗口读取或结果缓存。

#### <u>2. 缓存和预加载的取舍由容量、正确性与权限共同决定</u>

增大 OpenLayers 瓦片缓存或设置更积极的 `preload` 可能改善返回旧区域和缩放过渡，也可能消耗额外网络、图像解码和 GPU 内存。HTTP Cache 还受到 URL、Vary、max-age、权限和更新策略限制，不能把公开底图的 `public` 直接用于私有能源图层。Node Source 的原始 Raster 和 PNG Map 还要考虑源文件更新与进程重启。缓存越长越容易过时，缓存不是免费容量。

#### <u>3. 分层渲染的细粒度改动要由帧数据决定</u>

例如当前 marker 每次点击会 `clear()`、创建 Feature、`addFeature()`；可以评估复用 `Feature.geometry.setCoordinates()`，但只有一个标记点时可能属于收益极低的微优化。英文国家注记的样式函数会创建 Style/Text 等对象，大量要素时可以试验样式对象复用、裁剪与聚合。数据源更新隔离不代表 GPU 绝对只重绘一层，需要主线程和帧证据才能确认收益。
