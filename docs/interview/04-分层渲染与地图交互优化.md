## 12. 为什么能源地图需要栅格与矢量分层？基础地图、能源热力图、交互标记和弹窗分别如何渲染？

### 【回答要点】

区分四类内容：XYZ 底图/行政边界/地名、TileWMS 大规模能源热力分布、VectorLayer 少量可交互 Feature，以及 Vue DOM 信息弹窗。比较图片与独立矢量几何对象的数据规模、前端解码/样式/渲染负担；给出具体图层源码、职责和选择依据。**分层的好处是数据表示及操作职责隔离，不保证所有图层都能独立 GPU 重绘。**

本题承接前两条优化主线：TileWMS / TileGrid 回答“当前视图应该获取哪些地图资源”，业务缓存、Promise 去重和取消回答“哪些网络请求可以复用或停止”；**分层渲染进一步回答“资源到达后，浏览器需要管理、更新和绘制哪些对象，以及一次局部变化是否需要重建无关数据”**。

分层渲染不是单纯增加 Layer 数量，更不是承诺浏览器只重绘发生改变的那一层。它的核心是按**数据规模、绘制方式、更新频率和交互职责**拆开数据源与图层，使大范围的能源分布展示与小范围、高频的交互操作采用不同的数据和更新机制。

~~~text
全球能源分布与交互展示
    ↓
地理底图 / 行政边界 / 地名注记（XYZ / Tile 图层）
    ↓ 作为地理参照，随视图按需获取并复用图片
能源热力图（TileWMS / Tile 图层）
    ↓ 以服务端生成的栅格 PNG 表示大范围连续能源数值
交互标记点 / 部分地理文字（VectorSource / VectorLayer）
    ↓ 仅维护需要在前端选择、定位和更新的少量 Feature
能源数值弹窗（Vue HTML）
    ↓ 使用单独的组件状态与像素坐标更新信息展示
最终由 OpenLayers 组织图层绘制；HTML 弹窗由浏览器 DOM 渲染
~~~

具体优化可以沿五个角度展开：

| 优化角度 | 核心机制 | 当前可证实的实现 | 仍需区分的边界 |
| --- | --- | --- | --- |
| 栅格与矢量分工 | 大规模连续分布交给栅格瓦片；少量交互对象交给矢量要素 | 能源 TileWMS、底图/注记瓦片、marker VectorLayer | 并非所有行政边界都作为矢量 Feature 加载 |
| 数据更新职责隔离 | 交互更新只修改对应 Source，不因一个标记点变化重取能源 PNG | markerSource.clear() + addFeature()；能源图层使用独立的 qgjMapSource | 不等于 GPU 完全不绘制其他图层 |
| 当前场景按需显示 | 语言、缩放范围和业务状态控制实际图层集合 | getBaseLayersByLocale()；部分图层配置 minZoom/maxZoom；业务图层按路径创建 | 未实现完整的全球→省市县多精度矢量分级加载 |
| 细粒度对象更新 | 复用已有 Feature / 样式 / 图层可减少对象分配和数据源重建 | 现有 marker 每次点击仍是 clear → new Feature → addFeature | Feature 原位更新是进一步改进方案，不可当作已实现 |
| 图层生命周期与代价控制 | 管理图层重建、预加载、可见性与绘制叠加 | watch 中重建 WMS 图层、setLayers；注记层 preload: Infinity | 更多图层和更积极的预加载不天然更快，需实验验证 |

### 【重点回答】

针对全球清洁能源开发潜力评估系统的渲染性能，我主要从**栅格与矢量分工、图层更新职责隔离，以及按业务场景控制图层内容**三个方面进行设计。

首先是绘制方式的选择。全球能源数据覆盖范围大、栅格单元多，如果将大规模连续能源分布逐个转换成前端矢量 Feature，会增加几何对象管理、样式计算和浏览器绘制的成本。因此系统使用 TileWMS 将大范围能源数据交由地图服务端生成栅格瓦片图片，前端按视图加载；用户点击后的标记点则使用独立的 VectorLayer 和 VectorSource 管理。这样，大规模数据展示不需要依赖海量前端交互对象，少量需要动态更新的要素仍保有精确交互能力。

其次是更新职责的隔离。能源热力图和交互标记分别维护数据源。用户点击地图时，主要更新 markerSource，并使用独立的点位查询接口获取能源数值，无需仅因为标记变化就重新请求整张能源热力图。能源信息弹窗也由 Vue 的 HTML 状态单独更新。这减少了局部交互导致无关数据重建和资源重新获取的需要；至于 OpenLayers 实际重绘了多少图像或合成层，仍需要通过浏览器性能分析验证，不能简单说分层后一定只重绘一层。

最后是图层生命周期与内容控制。项目会根据中英文模式选择不同注记图层，部分图层具有缩放可见范围，能源业务图层按当前所选数据路径动态装配。在此基础上还可以继续评估单个标记 Feature 的原位更新、样式对象复用、业务 WMS 图层的参数更新与缓存保留，以及瓦片预加载规模等细粒度优化；这些尚未全部在当前代码中落地，需要通过实际对照测试决定是否值得实施。

整体来看，**分层渲染的核心价值不是图层数量增加，而是让大范围、相对稳定的能源数据与小范围、频繁变化的交互数据采用不同的绘制表达和更新粒度**。这样可以避免把每次用户点击都扩展成整个能源地图的数据重建，并为进一步降低主线程计算、图片解码与交互绘制成本提供清晰的优化边界。

#### <u>1. 每类数据为什么选择不同的数据源</u>

全球风能、太阳能分布等原始数据通常是大范围栅格。若将大量栅格单元逐个转为前端 `Feature`，浏览器就要承担几何对象管理、样式构建、状态维护和要素绘制成本；而宏观热力图并不要求每一个栅格单元都具备独立的前端交互能力。

因此当前项目选择让服务端根据 WMS GetMap 请求生成能源栅格图片，前端通过 `TileWMS` 作为 `Tile` 图层加载。关键源码见 [Map2D.vue](../../apps/web/src/components/dataService/Map2D.vue)：

~~~javascript
const qgjMapSource = new TileWMS({
  url: `${baseURL}/map/getmap`,
  params: {
    SERVICE: "WMS",
    VERSION: "1.1.0",
    REQUEST: "GetMap",
    Map: props.qgsMapPath,
    LAYERS: props.tifMapPath,
    FORMAT: "image/png",
    CRS: "EPSG:4326",
    language: locale.value,
  },
  tileGrid: customTileGrid,
});

// createQgjZoomLayer1 的返回值
return new Tile({
  zindex: 2, // 当前源码的原始写法；此处大小写不符合 OpenLayers zIndex 选项
  title: "渲染地图",
  source: qgjMapSource,
  minZoom: 0,
  maxZoom: 12,
});
~~~

上述片段的重点在 `source: qgjMapSource`：图层承载的是服务端已渲染好的 PNG 瓦片，而不是浏览器侧海量 GeoTIFF 像元对象。因此前端无需逐像元创建可交互几何要素；每张图片仍然要经过网络获取、解码、纹理/绘制资源管理和地图叠加，并不是零渲染成本。

对于用户点击后需要显示的红色标记点，项目单独配置轻量的矢量数据源：

~~~javascript
const markerSource = new VectorSource();
const markerLayer = new VectorLayer({
  zIndex: 100,
  source: markerSource,
  style: new Style({
    image: new Circle({
      radius: 6,
      fill: new Fill({ color: "red" }),
      stroke: new Stroke({ color: "white", width: 2 }),
    }),
  }),
});
~~~

`VectorSource` 管理少量 `Feature`，使精确位置、样式和交互可以由客户端灵活更新；与能源分布图片的职责分离。底图、边界和中文注记主要也是 XYZ / Tile 图层，英文国家名称另使用 GeoJSON 驱动的 `VectorLayer`。这不是“所有地理信息都交给同一矢量层”，而是**不同数据按展示与交互需要选择不同渲染表达**。

这项机制的工程价值是减少浏览器维护大规模几何对象的需求；但实际省去了多少 JS、内存和帧时间，需要根据假设对照测试，不能用项目采用 WMS 直接证明某个性能百分比。

#### <u>2. 渲染层与业务展示层如何分开</u>

当前项目 `<div id="mapView">` 中挂载 OpenLayers Map，由 Tile 与 VectorLayer 组合空间要素；能源数值的 `coordinate-popover` 使用 Vue HTML，根据 `showPopover`、`identifyNumResult`、`popoverStyle` 显示和定位，**不是把所有业务说明文字嵌入能源 PNG**。这使能源栅格图片的更新与 DOM 信息弹窗变化有不同入口。

## 13. 为什么点击一个能源点位不需要重新请求整张热力图？分层更新是否意味着 GPU 只重绘当前图层？

### 【回答要点】

从用户点击开始追踪 `markerSource.clear()`、`new Feature`、`addFeature()`、`identifyNum()` 和 Vue 弹窗状态；说明独立 `VectorSource` 与 `TileWMS` 数据源的职责隔离，证明**一次标记变化本身不修改能源热力图 Source 参数，也不要求重新发出全部 GetMap**。进一步区分数据源不重建、网络不回源、实际 OpenLayers 绘制/合成不是一回事。

### 【重点回答】

分层以后，第二个关键收益来自更新职责的分离：同一个地图视图包含能源图片、基础地理信息与交互标记点，但这些内容有不同的变更原因。

当前项目在点击时调用 `addMarker`：

~~~javascript
const addMarker = (coordinate) => {
  markerSource.clear();
  rawMarkerCoordinate = coordinate;
  const normalizeCoord = normalizeCoordinate(coordinate);
  marker = new Feature({
    geometry: new Point(coordinate),
  });
  markerSource.addFeature(marker);
  // 后续更新坐标状态并广播 clickedCoordinate2D
};
~~~

事件链路是：

~~~text
用户点击能源地图
    ↓
OpenLayers click 事件 → handleMapClick()
    ↓
addMarker() 修改 markerSource
    ↓
markerLayer 的要素发生变化，OpenLayers 安排相应地图渲染
    ↓
identifyNum() 通过独立 /map/getpoint 接口查询能源数值
    ↓
结果返回后更新信息弹窗，并在有效点击中广播 mapPointSelected
~~~

这里没有因为 `markerSource.clear()`、`markerSource.addFeature()` 去调用 `qgjMapSource.updateParams()` 或重建 `qgjZoomLayer1`。所以**在地图视图与能源图层参数不变的前提下，一次点击的标记更新本身不要求重新向 WMS 请求热力图 PNG**。这个结论可以从相互独立的 Source 及调用关系推导。

但是，**“不重新请求或生成能源图片”不等于“地图其他图层在 GPU 上绝对不会被再次绘制”**。OpenLayers 会协调地图帧、绘制与合成；能否缩小真实绘制工作量，必须通过浏览器 Performance、OpenLayers 渲染事件或底层图形性能证据确认。准确的面试表述应是“分离数据源，减少无关资源重取和数据重建”，而不是未经验证地承诺“只重绘一个 Layer”。

弹窗也与地图要素数据源分开。页面模板中的 `coordinate-popover` 是 Vue HTML 节点，由 `showPopover`、`identifyNumResult` 和 `popoverStyle` 等组件状态驱动；它不是所有点位数值都嵌入 WMS 图片。这让用户交互信息可以由业务数据更新驱动，无需重新渲染能源图片。地图移动后的位置计算与防抖机制已在前一题分析。

#### <u>1. 点击链路中的三种更新对象</u>

~~~text
用户点击 → Marker VectorSource 改变（地图几何要素）
         → getPointData 请求返回能源值（业务数据）
         → Vue 弹窗状态更新（DOM 信息展示）
    ↓
能源 TileWMS Source 的图层地址与 params 没有因标记变化而被重新配置
    ↓
已有能源瓦片仍可按照 OpenLayers 的数据源状态复用
~~~

一个 marker 的修改会触发 OpenLayers 渲染帧，地图其它图片是否重绘、绘制多少、是否只做合成，取决于实际渲染器与状态，需通过 Performance/图层绘制数据验证；不能在面试中把“无需重新生成能源热力图片”夸大为“仅重新绘制矢量图层且 GPU 完全不会触碰底图”。

## 14. 地图怎样根据语言、缩放级别和能源类型控制图层？什么时候重建图层，什么时候复用已有图层？

### 【回答要点】

读取 `getBaseLayersByLocale()` 的基础图层集合、`TileLayer.minZoom/maxZoom`、业务路径变化的 `watch`、`createQgjZoomLayer1()`、`layers.splice` 与 `map.setLayers`。说明哪些图层对象可以被复用、哪些需要因为源参数变化重新取图片；指出当前部分 `zindex` 大小写错误、注记 `preload: Infinity` 的网络/内存代价、以及高亮图层在不同分支装配行为。区分实际已有条件切换与设想中的全球→省市县多精度矢量数据裁剪。

### 【重点回答】

分层之后，还可以根据语言、缩放级别、场景选择实际需要的内容，而不让全部图层长期同时参与展示。

项目通过 `getBaseLayersByLocale` 生成不同的基础图层组合：

~~~javascript
function getBaseLayersByLocale(localeVal) {
  if (localeVal === "english") {
    return [
      tiandiMapLayer,
      tiandituBoundaryLayer,
      markerLayer,
      countryPointLayer,
    ];
  } else {
    return [
      tiandiMapLayer,
      tiandituMessageLayer,
      tiandituBoundaryLayer,
      markerLayer,
    ];
  }
}
~~~

这里底图与边界是复用的基础图层；中文模式主要使用中文瓦片注记，英文模式则加入国家名称矢量注记。**业务上不需要的另一种注记不会被同时放进当前基础图层集合**，可以减少当前场景里不必要的图层显示及相应资源需求。

另外，能源业务 Tile 图层配置 `minZoom: 0`、`maxZoom: 12`，中文注记等图层也有对应的可见缩放范围。OpenLayers 可根据当前视图的缩放条件决定图层是否参与显示。应将其理解为**可见性条件控制**，不能推导出项目已经为全球、省、市、县分别加载了不同矢量精度的数据集。

当前代码还根据 `qgsMapPath` 和 `tifMapPath` 决定是否装配能源业务层：没有有效业务路径时只设置基础图层，有路径时通过 `layers.splice(1, 0, qgjZoomLayer1.value)` 加入能源瓦片层；这属于按业务数据上下文组装图层。

至于“全球视图只显示国家边界、省级视图加载市县轮廓、近景再装配高精度要素”，是此机制可以继续演进的方向。当前 `getLevelByZoom` 根据缩放级别为**点位查询结果的图表联动**选择行政层级，不应错误描述为已经实现了行政边界 Feature 的多精度按级加载。

#### <u>1. 图层组装、重建与资源成本</u>

更多 Layer 不一定更快。每个额外的数据源或图层都可能带来瓦片加载、图像解码、样式计算、对象管理和图层叠加成本，因此需要关注何时创建、何时复用和何时销毁。

当前能源图层切换由 `watch(() => [props.qgsMapPath, props.tifMapPath])` 驱动：

~~~javascript
if (map.value && newQgs && newTif) {
  closePopover();
  markerSource.clear();
  qgjZoomLayer1.value = createQgjZoomLayer1();
  const layers = getBaseLayersByLocale(locale.value);
  layers.splice(1, 0, qgjZoomLayer1.value);
  map.value.setLayers(layers);
}
~~~

这段逻辑按业务图层路径重新创建 WMS Layer/Source，并使用已创建的底图等基础图层对象组装集合；它**没有每次重新构造全部基础图层实例**。但重建业务 Source 会影响原 Source 的瓦片缓存复用。因此对于仍需保持同一图层、只是部分 WMS 参数变化的场景，可评估复用 Source/Layer、按条件执行 `updateParams()`；如果切换的是不同能源图层，旧瓦片并不适合无条件继续复用。

中文注记 Tile 图层设置了：

~~~javascript
const tiandituMessageLayer = new Tile({
  source: tiandituMessageSource,
  preload: Infinity,
  // 当前代码还包含 updateWhileAnimating、updateWhileInteracting 等字段
});
~~~

`preload: Infinity` 表示允许预加载更低分辨率的瓦片级别，帮助缩放时使用已有较低精度图片过渡，但它也可能增加图片请求、内存和解码开销；**不代表预取全球所有瓦片**。适合通过 `preload: 0`、有限级别和当前策略做对照实验，而不是把积极预加载直接视为性能成果。

同时，需要注意部分 Tile 图层代码使用了 `zindex`（小写 `i`），而 OpenLayers 的选项名称应为 `zIndex`。这类拼写不一致可能导致设计的图层层级未按预期生效，实际叠加还取决于图层集合顺序。这是当前源码可以定位的配置问题，不应把所有原有层级设置都描述为已正确生效。与此相关，`highLightLayer` 的创建并不等于每次业务图层加载都会加入它：正常业务路径中的 `layers.push(highLightLayer)` 被注释，但语言切换分支存在加入高亮层的路径，需要按具体分支核对实际可见集合。

#### <u>2. 具体取舍与代码验证条件</u>

切换不同能源图层时旧热力图瓦片通常不适用于新图层，因此重建业务 Source 可能有正当理由；同一个能源图层只更新部分样式或语言参数时可以评估 `TileWMS.updateParams()`，但是参数变更是否引起当前 URL 和缓存键变化应再检查。不能简单声称“保留 Source 就一定没有瓦片请求”。图层卸载、ObjectURL 撤销、事件取消和 DOM 状态清理也应纳入独立生命周期管理。

## 15. 地图拖拽、缩放以及世界环绕时，怎样更新标记点与弹窗位置，避免无效业务计算和定位异常？

### 【回答要点】

区分三种坐标：地理经纬度、OpenLayers 地图视图坐标、地图容器像素/浏览器视口像素；考虑 EPSG:4326 世界横向环绕时同一地理点可能存在多个可见副本。解释 `normalizeCoordinate`、`wrapPixel`、`updatePopoverPosition`、`handleViewChange`、`moveend` 与 `debounce` 的调用时机和作用。要准确说明 100ms 防抖发生在**业务回调**上，不是整个 TileWMS 网络请求的统一节流。

### 【重点回答】

用户点击地图位置时，OpenLayers 提供的是当前地图的点击坐标；世界地图可水平重复，因此同一个地理点可能有不同的世界副本坐标。项目使用 `normalizeCoordinate` 把查询用经度映射回标准范围，同时保留点击时原始坐标用于 marker/世界副本显示，避免同一用户操作在点值查询和可见像素之间出现不一致。

[Map2D.vue](../../apps/web/src/components/dataService/Map2D.vue) 的主要交互链路：

~~~text
点击当前世界副本上的某一点
    ↓
event.coordinate → normalizeCoordinate → getPointData
    ↓
addMarker() 保存原坐标并更新 VectorLayer 的 Feature
    ↓
map.getPixelFromCoordinate() 得到地图容器像素
    ↓
wrapPixel() 或世界副本选择使弹窗靠近当前可见标记
    ↓
updatePopoverPosition()
    ├─ POPOVER_OFFSET：在点击点周围设置偏移
    ├─ mapView.getBoundingClientRect()：获得容器相对视口位置
    ├─ 容器像素转换成视口像素
    └─ 按窗口宽高与安全边距约束弹窗位置
    ↓
用户再次拖动/缩放 → moveend → 防抖业务回调
    ↓
重新计算当前 extent 与 resolution
    ↓
检查 marker 可见性；若可见，计算可能的世界副本
    ↓
选择当前可见副本，再更新弹窗像素位置和坐标广播
~~~

弹窗在 Vue 模板中是普通 HTML 组件，坐标不能直接当成 CSS 像素；`map.getPixelFromCoordinate()` 获取的是地图内部容器像素，`getBoundingClientRect()` 提供视口定位参考，二者需要结合弹窗定位方式换算，并在容器边缘裁剪，避免弹窗越过窗口边界。

#### <u>1. 当前源码的 moveend 与 debounce 是什么机制</u>

[Map2D.vue](../../apps/web/src/components/dataService/Map2D.vue) 为 `moveend` 绑定业务回调，并通过 Lodash 的 `debounce` 合并短时间内连续触发的回调：

~~~javascript
const handleViewChange = _.debounce(() => {
  const view = map.value.getView();
  const mapSize = map.value.getSize();
  const extent = view.calculateExtent(mapSize);
  const resolution = view.getResolution();

  // 判断标记点是否仍然可见、更新弹窗位置与坐标广播
}, 100);

map.value.on("moveend", handleViewChange);
~~~

`moveend` 表示地图移动结束后的事件，不是每一帧都触发的绘制事件。这里的 100ms 防抖约束的是**标记点可见性检查、弹窗重新定位及坐标状态广播**等业务处理，不是所有 `TileWMS` 底层 HTTP 请求。因此“拖拽缩放时对瓦片网络请求加了 100ms 防抖”不符合源码。

#### <u>2. 状态和渲染的不同成本</u>

这条链路中的耗时主要来自地理坐标变换、可见性判断、世界副本匹配、DOM 读写与 Vue 状态更新，不是“每拖动一帧都要重新向 GIS 下载全部热力图”。`moveend` 代表视图一次移动结束，属于已做的业务更新控制；如果要求拖拽过程中弹窗持续精准跟随，则还要另行设计轻量高频定位，不能以全部逻辑延迟到 moveend 取代实时跟随的产品要求。

## 16. 如果交互要素增长到数万条，应该怎样进一步优化 VectorLayer、样式计算与绘制更新？

### 【回答要点】

先说明当前项目没有把大规模能源原始栅格以海量前端 Feature 展示，且 marker 只有很少的交互要素；当前 `addMarker` 每次仍通过 clear/new Feature/addFeature 更新。随着对象规模变化，再考虑 Feature 原位更新、样式对象缓存、视图裁剪/聚合、分尺度数据、交互与动画期间的更新策略，必要时研究更适合大规模渲染的实现。所有方案必须能区分“当前代码已落地”与“后续可以选择”，并用帧/CPU/内存测量决定收益。

### 【重点回答】

分层提供了局部更新的组织边界，但实际是否做到细粒度更新，还取决于对 Source / Feature 的使用方法。

当前 `addMarker` 每次点击都执行 `markerSource.clear()` → `new Feature(new Point(...))` → `markerSource.addFeature(marker)`。这条链路简单且正确，却会在连续点击时产生新的 Feature/Geometry 对象和数据源变更事件。

如果业务始终只保留一个标记点，可以评估**在现有标记存在时只更新坐标**：

~~~javascript
// 改进方案示意：与上面当前源码不同，尚未落地
function updateMarker(coordinate) {
  if (!marker) {
    marker = new Feature({ geometry: new Point(coordinate) });
    markerSource.addFeature(marker);
  } else {
    marker.getGeometry().setCoordinates(coordinate);
  }
}
~~~

这样不再每次创建并删除同一种标记对象，减少对象分配与数据源增删操作；但坐标变化仍需触发地图更新，不能称为“完全不重绘”。当前只有一个红色标记点，收益可能很有限，在没有测量之前不应宣称明显提升帧率。

另外，英文国家名称图层目前用如下函数为每个 Feature 计算样式：

~~~javascript
const countryPointLayer = new VectorLayer({
  zIndex: 10,
  source: new VectorSource({
    url: "/map/国家点.json",
    format: new GeoJSON(),
  }),
  style: function (feature) {
    return new Style({
      text: new Text({
        font: "normal 14px 微软雅黑",
        text: feature.get("NAME") || "",
        fill: new Fill({ color: "#222" }),
        stroke: new Stroke({ color: "#fff", width: 2 }),
        offsetY: -12,
      }),
    });
  },
});
~~~

这意味着样式函数被调用时会构造新的 `Style` / `Text` / `Fill` / `Stroke` 对象。如果国家点要素较多或样式计算频繁，可以考虑缓存同名样式对象、复用共同样式配置，必要时评估标注碰撞、过滤与显示层级。这属于**可改进空间**，并非当前已经采用了样式缓存。

这里还要区分“局部业务变化”和“底层绘制优化”：前者可由源码中独立 Source 和 Feature 操作验证，后者需要性能数据才能确认效果。

#### <u>1. 分层设计仍可能产生的绘制负担</u>

如果把大量矢量 Feature 长期留在同一 Source，即使视觉上某些要素位于视图之外，框架仍要维护对象和索引，并可能发生样式计算与可见性查询；大量重叠注记还会提高布局与绘制成本。常用处理包括：在数据层按视图范围过滤、使用聚合减少当前需要绘制的对象、让远景选择低精度数据、尽可能复用样式实例与现有 Feature，并在性能指标表明必要时才更换图形渲染策略。

**当前项目不是已经实现了“万点矢量聚合”。** 仅凭样式函数或 Source 数据类型不能推出这一点；当前代码的 `countryPointLayer` 使用 GeoJSON 作为数据源并在样式函数内新建对象，这可以作为评估样式复用的切入点。

#### <u>2. 用什么证据验证分层渲染收益</u>

应把“职责分离可减少无关更新”与“性能已经显著提升”分开。对现有代码能够观察与验证的案例包括：

| 验证场景 | 应检查的执行链路 | 证据或指标 |
| --- | --- | --- |
| 不改变视图时连续点击不同点位 | markerSource 发生变更，但 WMS 参数是否保持不变 | `/map/getmap` 是否额外请求、Feature 创建次数、点击处理耗时 |
| 地图持续拖动和缩放 | 缺失瓦片获取、已缓存瓦片复用与图层重绘 | Network 请求数/字节、Frame Time P95、LoAF/长任务、图片解码耗时 |
| 中文/英文图层切换 | 图层集合、注记数据源和能源业务层如何重建 | 图层实例创建数、资源请求量、旧图片可复用性 |
| 只更新一枚标记点 | `clear + new Feature` 对比复用 `setCoordinates` | JS 执行耗时、分配数量、数据源更新次数、帧耗时 |
| 注记预加载策略变更 | 不同 `preload` 值对网络和缩放体验的影响 | 缩放时白块/等待时间、额外瓦片数量、峰值内存 |
| 注记数量较大时的样式处理 | 每次调用是否重新构建 Style 对象 | 样式调用次数、JS CPU、内存与交互帧耗时 |

需要使用浏览器 Network 与 Performance 共同判断。若点击标记点时没有新的能源 WMS 请求，能证明资源请求与交互数据更新进行了隔离；**不能仅凭这个网络结果证明 GPU 没有重新绘制能源层**。比较 Frame Time P95、主线程长任务、要素数量和内存，才能判断渲染层面的真实收益；测试应固定区域、视图尺度、数据量和交互路径。

当前资料没有提供足以单独证明“分层后帧耗时下降多少”或“某方案使 FPS 提升多少”的可信对照，故不编造具体改善比例。

#### <u>3. 本题及分层渲染体系的完整实现边界</u>

1. **分层显示不等于完全独立的 GPU 绘制**：源码能够证明不同 Source 的独立性，却不能仅凭 Layer 拆分保证 OpenLayers 不重绘其它层。应分开验证数据重建、网络请求和实际帧绘制。
2. **TileWMS 栅格与 VectorLayer 矢量是职责选择，不是技术优劣排名**：WMS 适合大范围连续热力分布；矢量适合需要独立样式、选择、几何处理的要素。若要素数量、精度与交互需求改变，选型也要重估。
3. **当前标记点没有实现 Feature 复用**：实际代码每次 `clear → new Feature → addFeature`；`setCoordinates` 的原位更新仅是可选优化方案。不能把旧项目分析中的“已复用已有要素”直接当作当前源码事实。
4. **按语言换图层与按缩放筛选查询区域不同**：前者可由 getBaseLayersByLocale 直接验证；`getLevelByZoom` 是查询联动的行政层级选择，不是已实现的 GeoJSON 多级精度裁剪。
5. **当前图层配置有值得复核的问题**：部分 `zindex` 与正确的 `zIndex` 不一致；`preload: Infinity` 可能增加资源开销；业务 WMS Source 重建会影响原瓦片缓存复用；高亮图层在不同分支装配行为不完全一致。
6. **尚缺独立的分层渲染收益测试**：应以固定数据和操作对照请求次数、Feature/Style 分配、帧时间与内存，不能用“分层”二字替代真实性能指标。

从本题自然延伸的追问是：**（1）浏览器在 OpenLayers 中实际怎样处理栅格瓦片、矢量要素及图层合成，局部 Source 变化会触发哪些工作？（2）如果业务从一个交互标记扩大到数万点位，应该怎样从 VectorLayer 继续演进到裁剪、聚合、批量更新或更适合的大规模图形渲染方案？**
